## 🧭 جدول التوجيه الإلزامي (نوع المهمة ← المهارة)

> **على كل وكيل:** قبل بدء أي مهمة، صنّفها على هذا الجدول، حمّل المهارة المطلوبة، وأعلنها في أول سطر:
> «المهارة المستخدمة: `اسم-المهارة`» — ثم سلّم بالدليل الذي تفرضه المهارة.

### ⚙️ إزاي المهارة «بتشتغل» عملياً؟ (اقرأها مرة وتعرفها دايماً)

المهارة **مش برنامج بينفّذ نفسه** — هي كتيّب تعليمات بيقراه الوكيل جوه دماغه قبل الشغل. ليها ٣ طرق تشغيل حسب الأداة:

| مكان الشغل | طريقة التشغيل | المطلوب منك |
|---|---|---|
| 🤖 أدوات فيها تشغيل تلقائي (Copilot coding agent، Codex، Cursor) | بتقرأ `.agents/skills/` من جوه المستودع **تلقائياً** عند بدء المهمة — عشان كده زامنّا المهارات جوه كل مستودع | لا شيء — بس لاحظ سطر «المهارة المستخدمة» في ناتجها |
| 🟣 Claude Code | بيقرأ `.claude/skills/` (موجود حالياً في malek بس) | حالياً: مفيش تغيير؛ لو هتشتغل بيه على مستودع تاني قوللي وأنا أعمل مرآة |
| 💬 جلسات محادثة (Arena وغيرها) | الوكيل يقراها من المستودع لما تطلب منه — استخدم جملة البداية تحت | انسخ جملة البداية مع المهمة |

**جملة البداية الجاهزة لأي مهمة في أي جلسة:**
> «افتح `.agents/skills/` في المستودع، اختار المهارة المناسبة من جدول التوجيه في `command-center-/skills/README.md`، ابدأ بسطر «المهارة المستخدمة: …»، ونفّذ بدليلها — والتسليم بالدليل اللي تفرضه المهارة.»

| لو المهمة… | المهارة الإلزامية | متى بالضبط؟ |
|---|---|---|
| 💻 **برمجة**: ميزة/إصلاح يمس أكثر من ملف | `implementation-planning` ← ثم `test-driven-development` | قبل كتابة أي كود، وبسراية الـ TDD أثناءه |
| 🔗 استخدام مكتبة/إصدار/API خارجي (Supabase، Next، Vite…) | `source-driven-development` | أي ادعاء عن سلوك مكتبة يختلف بين إصدارات |
| 🔍 **تدقيق كود** قبل دمج | `code-review` | بعد اكتمال أي تغيير وقبل البناء فوقه |
| 🐞 **تحليل**: خطأ/فشل اختبار/سلوك غريب | `systematic-debugging` | جذر المشكلة أولاً — ممنوع إصلاح بالتخمين |
| 🗄️ هجرة DB / RLS / دالة SQL / أداء استعلام | `database-postgres-rls` | أي لمس لمخطط أو سياسات أو منح |
| 💰 نقود: مدفوعات/أرصدة/إقفال يومية/تقنية مالية | `financial-correctness` | أي حاجة ليها معنى محاسبي (MALEK، LENA، Terranex، Kayyal، الضيافة) |
| 🎨 **تصميم**: شاشة/فورم/مكون يستخدمه عميل | `frontend-rtl-design` | كل منتجات المحفظة عربية RTL موبايل-أول |
| 🛡️ لمس مصادقة/صلاحيات/أسرار/مدخلات مستخدم | `security-review` | أي حد ثقة (trust boundary) اتلمس |
| ✅ قبل قول «الشغل خلص» | `verification-before-completion` | **دائماً** — بوابة الدليل |
| 🚀 قبل دمج في main أو إصدار | `release-readiness` | تعريف «جاهز» الرسمي للمحفظة |
| ⚖️ قرار معماري / مخالفة ADR / قرار مؤجل | `decision-governance` | ممنوع اختيار صامت — يُعرض على المالك |
| 🧪 إضافة/تعديل مهارة في هالمكتبة | `skill-engineering` | دستور المكتبة نفسه |
| 📣 تسويق Terranex | مهارة `terranex-ops` داخل مستودع Terranex | مقيدة بمشروعها — لا تُعمم |
| 🏛️ جرد/تدقيق المحفظة كاملة | دور المدير في `../AGENTS.md` + `../prompts/` | شغل مركز القيادة نفسه |

## ⛓️ السلاسل المعتمدة (متى تترابط المهارات)

```text
ميزة عادية:   implementation-planning → test-driven-development → code-review → verification-before-completion
                                              ↑                                         ↓
إصدار:        ... كله فوق + release-readiness ← security-review (لو حدود الثقة اتلمست) ┘
خطأ:          systematic-debugging → test-driven-development (اختبار رجعي) → verification-before-completion
قاعدة بيانات: database-postgres-rls + (مالية؟ financial-correctness) + verification-before-completion
واجهة:        frontend-rtl-design → verification-before-completion (+ screenshots بحسب المهارة)
```

## 📜 القواعد الملزمة

1. **الإعلان أولاً:** سطر «المهارة المستخدمة» قبل التنفيذ — مفيش شغل بدون مهارة معلنة.
2. **الدليل حسب المهارة:** كل مهارة تفرض شكل إثبات محدد (لقطات، خروج أوامر، مصفوفة اختبارات) — التسليم بدونه = غير مكتمل.
3. **الترمبوبية المحصورة:** مهارة واحدة إجبارية لكل مهمة كحد أدنى؛ السلاسل الموثقة فوق هي الوحيدة المسموحة تلقائياً، غيرها بقرار.
4. **المرجعية هنا:** عند اختلاف نسخة مستودع عن هذه المكتبة، **هذه تكسب** — ويُفتح تحديث للمستودع لاحقاً (موجة مزامنة).
5. **التطوير من الداخل:** أي تحسين لمهارة يمر بمهارة `skill-engineering` نفسها، ويتم هنا أولاً ثم ينسخ للمستودعات.

## 📂 الفهرس

| المهارة | الغرض في سطر |
|---|---|
| `implementation-planning` | تفكيك الشغل لخطوات صغيرة قابلة للاختبار قبل الكود |
| `test-driven-development` | الاختبار الأحمر أولاً — حديد: لا كود منتج بدون اختبار فاشل |
| `source-driven-development` | سلوك المكتبات = دليل يُتحقق من مصادره الرسمية، مش ذاكرة |
| `code-review` | مراجعة بمرورين (مطابقة + معمارية) وتصنيف خطورة وحكم |
| `systematic-debugging` | 4 مراحل: جذر ← نمط ← فرضية واحدة ← اختبار رجعي |
| `security-review` | مسارات إساءة واقعية على حدود الثقة + ثوابت المحفظة |
| `database-postgres-rls` | هجرات أمامية فقط، عزل RLS، SECURITY DEFINER منضبط |
| `financial-correctness` | معاني النقود منفصلة، حسابات عشرية، append-only |
| `frontend-rtl-design` | عربي RTL أصيل، موبايل أولاً، مصفوفة تحقق + أدلة لقطات |
| `verification-before-completion` | لا ادعاء إتمام بدون خروج أوامر طازج |
| `release-readiness` | مصفوفة «الجاهزية للإصدار» وحاجز الإيقاف stop-the-line |
| `decision-governance` | ADRs لا تُعدَّل — تُتجاوز بـ ADR جديد وبقرار المالك |
| `skill-engineering` | قواعد KEEP/MODIFY/MERGE/DELETE/MISSING للمكتبة |
